# K3 X100：BG1/Zc224 校验计算 RVV 优化

本次将已有 BG1/Zc384 的 RVV 校验计算方法扩展至 **BG1/Zc224**。保留原校验关系、数据展开布局、输出数量及位序；已有 Zc384 校验优化和输出打包优化继续保留。

## 实现与开关

- `vendor/openairinterface5g/openair1/PHY/CODING/nrLDPC_encoder/ldpc_bg1_z224_rvv.h`：从原 `ldpc224_byte_128.c` 提取46行、2109个异或操作数和输出位置，使用 e8/m2、四个独立累加器，每批最多64字节。
- 同目录 `ldpc_encode_parity_check.c`：只在 BG1 的 `case 224` 选择新函数；原函数作为回退保留。
- 仅 RVV 且非 AVX2/AVX512 输入布局时启用。定义 `XSAI_LDPC_DISABLE_RVV_BG1_Z224=1` 可独立关闭；Zc384 和输出打包仍有各自的禁用开关。

X100 的每行224字节分成64＋64＋64＋32字节；按实际VL推进，尾批不越界。中间字节可能包含多个码块对应的位，不能把批量字节数理解为空口新增的数据或校验比特。

## 构建与验证

新克隆者按项目指南安装依赖，再准备一个不存在的新 OAI 工作目录：

```bash
bash scripts/prepare-oai-worktree.sh "$HOME/xsai-oai-rvv"
```

按本机 OAI 构建流程配置上述源码目录；`OAI_BUILD` 应指向这个新源码对应的构建目录：

```bash
cmake --build "$OAI_BUILD" --target ldpc -j2
```

确认运行程序实际加载新构建的 `libldpc.so`。本仓库更新不会自动替换已有部署；新源码不等于现有二进制已经更新。

任意有 Python 的设备可检查新旧校验表、分支和回退：

```bash
python3 -m unittest discover -s tests -p 'test_ldpc*py' -v
```

在有 RVV 的 riscv64 Linux/K3 上进行原函数与新函数的逐字节对照：

```bash
python3 scripts/check-ldpc-z224-rvv.py \
  --oai "$HOME/xsai-oai-rvv" --build "$OAI_BUILD" --cc gcc-16 --cpu 0
```

检查脚本读取已有 OAI **Makefile** 构建的 `ldpc.dir/flags.make`；需要指定本机可用编译器和允许使用的 CPU，不承诺 Ninja 构建兼容。测试4组结构化输入和64组独立随机展开矩阵，每组10304字节输出与原版一致；输入设置只读，输出前缀及输入/输出末端设边界保护。该测试验证与原 OAI 实现等价，不是独立标准向量认证。

## 已完成的集成验证

2026-10-30 在 K3 完成：4项校验表/分支检查；68组原生函数对照；完整编码器翻译单元编译；Zc224禁用开关预处理检查；900个正式TB的全部编码输出与原生产编码器逐字节比较。

TB配置覆盖 Zc224、已有 Zc384、Zc240、BG2/Zc64，以及11码块Zc384。参考计算在性能计时之外。完整 codec 的 decoder 保留，测试使用独立动态库，不覆盖生产源码或库。此次没有进行全新 OAI 整项目构建、其他架构性能测试或真实空口验收。

## 单线程 benchmark

X100 CPU0、2.2GHz，50RB分配、106RB载波、MCS9、12符号、两个码块。三种种子，每种10次预热＋200正式TB，每版本600正式TB；每进程重复使用一份种子随机载荷，版本运行顺序交替。

两组均保留已有输出打包 RVV 优化和 Zc384 校验优化，仅 Zc224 校验计算不同。

| 指标 | 新增Zc224之前 | 新增Zc224之后 |
|---|---:|---:|
| 完整编码，μs/TB | 137.203 | 98.663 |
| 实测用户态CPU cycles/TB | 300013 | 214046 |
| 平均用核量 | 1.004 | 1.000 |

完整编码耗时下降 **28.09%**。周期来自 `perf_event_open` 硬件事件，非频率换算，仍含测量工具的小量开销。各版本完整 benchmark 的后续 PDSCH 检查通过，同种子的输入/输出哈希一致。

参数检查发现，同一 benchmark 的 MCS9/13符号选择 Zc240；本轮用12符号并记录实际 BG/Zc，以确保测试新分支。不能与旧 MCS14/13符号 benchmark 直接计算同条件收益。

## 旧条件 RFsim 全链路

沿用2026-10-26传统链路配置：106RB载波，实际上下行50RB，下行MCS9/QPSK，上行MCS14/16-QAM，band78、30kHz、SISO。配置SHA256：`435ac9e5f40651ad0a8ef4cfbd5832b5407297e4db336e707652d11ec5724f1d`。未额外注入AWGN或指定20dB噪声。

gNB和UE均允许使用 X100 CPU0–7、2.2GHz；这是多线程链路，不能称为单核或八核跑满。每版本至少约20秒预热，再约30.6秒正式采样。三组均确认 BG1/Zc224、两个码块、K4928。

| 原计时区域，μs/调用 | 未优化原版 | 已有优化、不含Zc224 | 新增Zc224后 |
|---|---:|---:|---:|
| 完整DLSCH encoding | 355.368 | 319.884 | 253.988 |
| LDPC enc parity | 224.445 | 221.231 | 154.587 |
| LDPC enc output | 34.786 | 4.057 | 3.989 |

新增 Zc224 后，完整编码相对已有优化版再下降 **20.60%**；相比本轮原版累计下降 **28.53%**。这是本轮三组对照，未混用10月26日的历史耗时。

原DLSCH计时边界：`nr_generate_pdsch()` 内 start_meas → `nr_dlsch_encoding()` → 返回后 stop_meas。窗口均值由原计时器累计耗时和调用数的首末差分计算，排除预热；子范围有嵌套，不能相加。RFsim 本轮未采集硬件周期，不作周期估算。

三组正式窗口内，UE上下行HARQ计数各增长4608，UE及gNB上下行错误计数均无增长。启动时已有一次UE错误，不应表述为从启动起全程零错误。测试服务已停止，生产文件散列值前后相同。

机器可读的条件、结果、校验范围与来源散列见 [实测记录](benchmarks/ldpc-bg1-z224-rvv-20261030.json) 和 [集成验证](benchmarks/ldpc-bg1-z224-integration-20261030.json)。这些是特定硬件和配置的实测结果，不保证其他规模和运行环境达到相同降幅。
